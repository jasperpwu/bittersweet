## Project Overview
Bittersweet — an iOS mobile app built with Expo 53 (React Native), TypeScript, Expo Router, and NativeWind (Tailwind CSS).

## Tech Stack
- **Framework:** Expo 53, React Native
- **Language:** TypeScript
- **Routing:** Expo Router (file-based, `app/` directory)
- **Styling:** NativeWind / Tailwind CSS
- **State:** Zustand (with persist via AsyncStorage)
- **Native extensions:** Custom Expo plugins (`plugins/`), patches (`patches/` via patch-package)

## Directory Map
- `app/` — Expo Router screens and layouts
- `src/components/` — Reusable UI components
- `src/modules/` — Feature-specific logic and components
- `src/services/` — External service integrations
- `src/store/` — Zustand stores
- `src/hooks/` — Custom React hooks
- `src/utils/` — Utility functions
- `plugins/` — Custom Expo config plugins (native-level changes)
- `patches/` — patch-package patches applied via `postinstall`
- `targets/` — Native widget extension source (Live Activity, Home Screen widgets). This is the primary location for widget/Live Activity Swift UI code.
- `ios/bittersweetmobile/` — Main app native code (ActivityKit handlers, intent implementations)

## Build / Dev Commands
- `npm run ios` — Run on iOS
- `npm run start` — Start Expo dev server
- `npm run prebuild` — Regenerate native projects
- `npm run lint` — ESLint + Prettier check
- `npm run format` — Auto-fix lint + formatting

## Bug Fixing Approach
When fixing bugs, follow this structured approach:
1. **Identify the root cause** — Read the relevant code and trace the data flow to understand *why* the bug happens, not just *what* happens.
2. **Map the reproduction flow** — Write out the exact sequence of steps/states that trigger the bug, identifying where the logic breaks.
3. **Propose a minimal fix** — Target the root cause directly. Avoid workarounds that mask the issue.
4. **When stuck, add targeted logs and ask the user to test** — If multiple root causes are plausible and code reading alone can't narrow it down (e.g., race conditions, async timing, native component behavior), add temporary `console.log` statements at key decision points, ask the user to reproduce the bug, and use the log output to pinpoint the actual cause before writing a fix.

## Conventions
- **Never hardcode colors.** Always use NativeWind/Tailwind theme tokens defined in `tailwind.config.js` (e.g., `text-light-text-primary dark:text-dark-text-primary`, `bg-light-bg dark:bg-dark-bg`). For inline styles where NativeWind classes aren't possible, reference the token values via a shared constants file or `useColorScheme()` with the config values — never raw hex literals.
- Always reference actual Expo and iOS docs; do not guess APIs or expect user to trial-and-error.
- `ios/` and `node_modules/` are not tracked. Never modify them directly — sync native changes through Expo plugins or patches.
- All native code (Live Activity UI, widgets, ActivityKit handlers, intents) belongs in `targets/` (git-tracked). `ios/` is fully generated by prebuild — never edit it directly.
- **Patching dependencies:** The correct workflow for changing a dependency's native/JS code is: (1) alert the user that you need to edit `node_modules/` for patch generation, (2) make edits in `node_modules/<package>/`, (3) run `npx patch-package <package-name>` to regenerate the patch in `patches/`. Always give the user a heads-up before touching `node_modules/` and explain that the edit is for patching — never leave `node_modules/` changes uncommitted without a corresponding patch.
- Do not blindly execute what the user asks. Validate and research first; let the user know if the ask is unreasonable.
- Do not execute alternative solutions without asking the user.
- Must let user know when it no longer safe to run `npx expo prebuild --clean`.
