## Project Overview
Bittersweet — an iOS mobile app built with Expo 53 (React Native), TypeScript, Expo Router, and NativeWind (Tailwind CSS).

## Tech Stack
- **Framework:** Expo 53, React Native
- **Language:** TypeScript
- **Routing:** Expo Router (file-based, `app/` directory)
- **Styling:** NativeWind / Tailwind CSS
- **State:** Zustand (with persist via AsyncStorage)
- **Native extensions:** Custom Expo plugins (`plugins/`), patches (`patches/` via patch-package)

## Directory Map
- `app/` — Expo Router screens and layouts
- `src/components/` — Reusable UI components
- `src/modules/` — Feature-specific logic and components
- `src/services/` — External service integrations
- `src/store/` — Zustand stores
- `src/hooks/` — Custom React hooks
- `src/utils/` — Utility functions
- `plugins/` — Custom Expo config plugins (native-level changes)
- `patches/` — patch-package patches applied via `postinstall`
- `targets/` — Native widget extension source (Live Activity, Home Screen widgets). This is the primary location for widget/Live Activity Swift UI code.
- `ios/bittersweetmobile/` — Main app native code (ActivityKit handlers, intent implementations)

## Build / Dev Commands
- `npm run ios` — Run on iOS
- `npm run start` — Start Expo dev server
- `npm run prebuild` — Regenerate native projects
- `npm run lint` — ESLint + Prettier check
- `npm run format` — Auto-fix lint + formatting

## Bug Fixing Approach
When fixing bugs, follow this structured approach:
1. **Identify the root cause** — Read the relevant code and trace the data flow to understand *why* the bug happens, not just *what* happens.
2. **Map the reproduction flow** — Write out the exact sequence of steps/states that trigger the bug, identifying where the logic breaks.
3. **Propose a minimal fix** — Target the root cause directly. Avoid workarounds that mask the issue.
4. **When stuck, add targeted logs and ask the user to test** — If multiple root causes are plausible and code reading alone can't narrow it down (e.g., race conditions, async timing, native component behavior), add temporary `console.log` statements at key decision points, ask the user to reproduce the bug, and use the log output to pinpoint the actual cause before writing a fix.

## Conventions
- **Never hardcode colors — enforced.** Always use NativeWind/Tailwind theme tokens defined in `tailwind.config.js` (e.g., `text-light-text-primary dark:text-dark-text-primary`, `bg-light-bg dark:bg-dark-bg`). For inline styles where NativeWind classes aren't possible (e.g. `Ionicons color=`, RN `style={{}}`, SVG), reference the token via `src/config/theme.ts` `colors` (kept in sync with `tailwind.config.js` — update BOTH when adding a token). **Raw hex literals, `bg-[#...]`/`text-[#...]` bracket classes, and default palette classes (`bg-gray-700`, `bg-blue-600`) are forbidden for UI chrome** (text, background, border, icon, button/accent colors).
  - **If no suitable token exists, STOP and ask the user before adding a new token or hardcoding** — do not invent tokens or drop a raw hex silently.
  - **Fix-on-touch:** whenever you edit a file, convert any chrome hex you add, change, or sit next to into tokens (don't rewrite the whole file — just what you touch and its immediate surroundings).
  - **Exception — data/brand palettes stay literal:** tag colors, avatar-color options, chart/series palettes, slider/fruit themes, and the fruit/apple brand accent `#E9A065`. These are data, not chrome; leave them (or ask if unsure which it is).
  - Standard button consolidation: use the shared `src/components/ui/Button` (variants `primary|secondary|outline|soft|ghost|destructive`, `fullWidth`, `loading`, `haptic`); keep list rows, nav cards, disclosure toggles, back buttons, segmented controls, and bare icon taps as `Pressable`.
- Always reference actual Expo and iOS docs; do not guess APIs or expect user to trial-and-error.
- `ios/` and `node_modules/` are not tracked. Never modify them directly — sync native changes through Expo plugins or patches.
- All native code (Live Activity UI, widgets, ActivityKit handlers, intents) belongs in `targets/` (git-tracked). `ios/` is fully generated by prebuild — never edit it directly.
- **Patching dependencies:** The correct workflow for changing a dependency's native/JS code is: (1) alert the user that you need to edit `node_modules/` for patch generation, (2) make edits in `node_modules/<package>/`, (3) run `npx patch-package <package-name>` to regenerate the patch in `patches/`. Always give the user a heads-up before touching `node_modules/` and explain that the edit is for patching — never leave `node_modules/` changes uncommitted without a corresponding patch.
- **Patching a package's JS API requires editing `build/`, not just `src/`.** Packages like `expo-live-activity` ship pre-compiled JS (`main: "build/index.js"`); Metro loads `build/index.js` and never reads `src/index.ts`. When adding/changing a JS export, edit all three: `src/index.ts` (source of truth), `build/index.js` (what actually runs), and `build/index.d.ts` (types). Editing only `src/` causes "X is not a function" at runtime even though TypeScript compiles fine. Patching `build/` is reproducible — patch-package diffs against the pristine npm tarball, so compiled output is captured in the patch like any other file.
- **Adding new Swift files to native targets:** New `.swift` files in `targets/HomeWidget/` are NOT automatically included in Xcode builds. They must be registered in `plugins/withHomeWidget.js` — add to `widgetExtensionFiles` (for the widget extension target) and/or `mainAppFiles` (for the main app target). If a file is used by code that compiles in both targets (e.g., `SessionIntent.swift` is in both), the new file must be added to both arrays. Run `npx expo prebuild --clean` after.
- Do not blindly execute what the user asks. Validate and research first; let the user know if the ask is unreasonable.
- Do not execute alternative solutions without asking the user.
- Must let user know when it no longer safe to run `npx expo prebuild --clean`.

## Data Sync Philosophy (Single-Device)
- **Lists** (sessions, tags, goals, badges): pull latest cloud data, compute diff, write finalized to cloud
- **Objects/values** (rewards, settings): pull latest, compare `updated_at`, latest wins, write to remote
- **On cold start** (`INITIAL_SESSION`): Merge — flush offline queue, pull from cloud, last-write-wins per entity
- **Grove drag-to-refresh**: Pull all grove social data from cloud
- All syncable data types: focus sessions, session tags, focus goals, badges, rewards, blocklist, settings
- **Sync logic belongs in slice methods** (`triggerSync`, `pullAndApply`), not in `_layout.tsx`. The layout should only call the slice method; all store updates, UserDefaults writes, and side effects (shield, widget sync) happen inside the slice. Do not duplicate sync logic across files.

## Auth Data Lifecycle Policy
How local data is treated on each auth transition (`onAuthStateChange` in `app/_layout.tsx`). The driving principle: **never destroy the only copy of a user's data, and never leak one user's data to another.**

- **Brand-new sign-up** → **preserve local data and upload it.** A user who built data before creating an account keeps everything. We can't ask Apple Sign-In whether the account is new (it auto-creates), so we detect it by probing the cloud: on `SIGNED_IN`, `pullFromCloud()` first — if the cloud has **no sessions and no tags**, it's a brand-new account (the signup DB trigger seeds only `profiles` + `rewards`, never tags/sessions), so call `initialUpload()` and do **not** clear anything.
- **Sign-in to an existing account** → **clear all local data, then pull the cloud clean.** If the cloud probe finds sessions/tags, treat it as a returning user: wipe local (see below) and `pullAndApply()` so the device exactly mirrors the cloud.
- **Sign-out** → **always wipe all local data** (privacy — no data may survive for the next person on the device).
- **User switch** (different `lastSignedInUserId` on `SIGNED_IN`/`INITIAL_SESSION`) → wipe local before adopting the new user.
- **"Wipe all local data" means everything**, via this exact sequence: (1) remove native restrictions + clear shield config, (2) `WidgetService.clearAllWidgetData()`, (3) `AsyncStorage.clear()` (then re-set the `bittersweet-installed` flag), (4) delete local photo files (`deleteAllSessionPhotos()` + `deleteAllPurchasePhotos()` — store state alone doesn't remove the JPEGs on disk), (5) `clearAllStoreData()` (sessions, tags, goals, badges, rewards incl. purchases/custom rewards, blocklist, subscription, referral, **shared-tag stats**, grove/challenge data, etc.), (6) `clearUnifiedStoreData()` (settings/preferences), plus `resetSyncSnapshot()` and `grove.resetGrove()`. When adding any new persisted state, make sure `clearAllStoreData` zeroes it too — an omission leaks data across accounts.
- **Detection is cloud-emptiness, not timestamps:** chosen because it makes data loss impossible — we only ever clear local when there is cloud data to replace it with.

## Offline Sync Queue & Snapshot Across Auth
The sync pipeline (`syncMiddleware.ts` + `SyncService` + `SyncQueue`) has three pieces of mutable state that must be reset correctly on every auth transition, or you get RLS error storms and cross-account leaks. Every syncable table's RLS is `WITH CHECK (auth.uid() = user_id)`, so **any write attempted without the matching session fails** with `42501 new row violates row-level security policy`.

- **`syncQueue` is an in-memory singleton, not just an AsyncStorage key.** `AsyncStorage.clear()` wipes the persisted `bittersweet-sync-queue` blob but the singleton keeps its in-memory `queue` array (`loaded` stays `true`). A later `flush()` then replays those stale rows — failing RLS after sign-out, or leaking the previous user's rows into the next account on a user switch. **Always call `syncQueue.clear()` on wipe** — it's bundled into `resetSyncSnapshot()`, which runs in every wipe path (sign-out, user-switch). Adding a new persisted queue/buffer? Reset its in-memory copy here too, not just via `AsyncStorage.clear()`.
- **`flush()` must verify a session before writing.** A debounced flush scheduled while authenticated can fire *after* the token is gone (sign-out, or a slow sign-in/out race). `SyncService.flush()` guards with `supabase.auth.getSession()` and no-ops when there is no user. This is the backstop — keep it; don't assume callers only flush while authenticated.
- **`pullAndApply()` (and any cloud-wins apply) must drop the diff baseline BEFORE applying**, via `invalidateSyncSnapshot()`. The middleware diffs new state against `lastSyncedSnapshot`; if you apply ~50 pulled cloud rows against an empty/stale baseline, it treats them as brand-new local rows and **re-enqueues the data you just downloaded**. Those phantom upserts are what then fail RLS if the user signs out before they flush. Re-baselining means "this pulled data IS the new baseline — don't push it back."
- **Two reset helpers, pick deliberately:** `invalidateSyncSnapshot()` drops the baseline + cancels the pending debounced flush but **keeps the queue** (use for cloud-wins applies — discard the pending local diff, preserve genuinely-queued writes). `resetSyncSnapshot()` does all of that **plus** `syncQueue.clear()` + blocklist baseline clear (use for full sign-out/user-switch wipes). Never clear the queue inside an apply path — it would drop unrelated pending writes.
- **`triggerSync()` (cold-start merge) intentionally does NOT invalidate the snapshot** — it's last-write-wins and *must* enqueue genuinely local-newer rows. Only cloud-wins applies re-baseline.

## Blocklist Architecture
- **Single canonical UserDefaults key:** The blocklist uses `"bittersweet-blocklist"` as the single canonical selection ID in UserDefaults. The picker (`DeviceActivitySelectionViewPersisted`), blocking (`blockSelection`), sync merge operations, and the Zustand store all use this same key. Never introduce a separate "merged" or "temp" ID that persists beyond a single sync operation — having two IDs for the same data leads to them getting out of sync.
- **When updating blocklist state after sync**, always update all three: (1) `currentSelectionId` in the Zustand store, (2) `blockedApps` with legacy token format (for badge counts), (3) `WidgetService.syncCurrentSelectionId()` (for native re-blocking). Missing any one of these causes subtle bugs (badge not updating, native intent can't re-block, etc.).

## Sync Mapper Symmetry
- **`rowToX()` must restore every field that `xToRow()` saves.** When adding a field to `xToRow()` (writing to DB), always add the inverse mapping in `rowToX()` (reading from DB). Missing fields in `rowToX()` cause silent data loss during sync — e.g., `updatedAt` not restored breaks last-write-wins merge, `deletedAt` not restored causes deleted items to reappear, `sortOrder` not restored loses user ordering.
